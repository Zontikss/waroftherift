# PLAN — поэтапный план разработки War of the Rift

Версия плана: 1 · Дата: 2026-10-24 · Платформа: Minecraft 1.20.1, Forge 47.x, Java 17.

Правило этапов: этап считается завершённым только когда (а) выполнены его критерии приёмки, (б) проект собирается реальной командой Gradle, (в) `docs/IMPLEMENTATION_STATUS.md` обновлён фактическими результатами. Нельзя переходить к этапу, если предыдущий не принят.

Общие «ворота качества» (Quality Gates), начиная с этапа 1:
- G1: `./gradlew build` без ошибок и без отключённых проверок.
- G2: `./gradlew runServer` стартует мод на выделенном сервере без клиентских классов, без исключений в логе (с этапа 1).
- G3: `./gradlew runClient` — мир создаётся и загружается (с этапа 1; выполняет пользователь или окружение с графикой).
- G4: JUnit для чистого ядра (с этапа 3).
- G5: GameTest / ручной сценарий для игровых систем (с этапа 4).
- G6: перезапуск сервера сохраняет состояние войны (с этапа 3).

## Этап 1. Каркас проекта и сборка — ФАЙЛЫ СОЗДАНЫ (2026-10-24), сборка проверяется в GitHub Actions

Примечание: так как у пользователя нет JDK 17 и Forge, этап 1 выполняется через CI (`.github/workflows/build.yml`: JDK 17 Temurin, `./gradlew build`, артефакт `waroftherift-jar`). Gate G1 считается пройденным только после зелёного запуска Actions.

Цель: рабочий Forge-проект, который собирается и стартует с пустым модом.
Зависимость внешняя: JDK 17 и доступ к Forge Maven / Gradle distributions / Mojang (в текущем окружении закрыт, см. STATUS).
Состав:
- Официальный MDK Forge 1.20.1-47.x (реальный Gradle Wrapper из MDK, не рукописный).
- `gradle.properties`: `mod_id=waroftherift`, `mod_name=War of the Rift`, `mod_version=0.1.0`, `mod_group_id=io.github.waroftherift`, mappings `official`/`1.20.1`.
- `mods.toml`: `loaderVersion="[47,)"`, зависимости `forge [47,)`, `minecraft [1.20.1,1.21)`; без ссылок на NeoForge/Fabric.
- `WarOfTheRiftMod` (`@Mod("waroftherift")`, mod event bus через `FMLJavaModLoadingContext.get().getModEventBus()`), `LogUtils`.
- Каталоги ресурсов и `en_us.json` / `ru_ru.json` только для существующих ключей; `pack.mcmeta`.
- `README.md`.
Приёмка: G1, G2; JSON валиден; Java toolchain = 17; в проекте нет NeoForge/Fabric.

## Этап 2. Конфигурация и фракции

- `WarOfTheRiftConfig` (тип SERVER для игровых параметров, CLIENT для UI; регистрация один раз в конструкторе мода).
- `Faction`, `FactionResolver` на тегах типов сущностей `data/waroftherift/tags/entity_types/faction/{settlements,illagers,nether_legion}.json` (датапак-расширяемо), кэш по `EntityType`, учёт исключений (приручённые/игроковые голем — см. A6 в ARCHITECTURE).
- Диагностика: команда `/waroftherift faction <entity>`.
Приёмка: юнит-тесты на разрешение фракций (на уровне ядра), G1–G2, тег-файлы валидны, моды-совместимость: неизвестная сущность → `NONE`.

## Этап 3. Сохраняемое состояние и журнал событий

- `WarSavedData` (Overworld), `data/model/*`, версия схемы + миграции, `setDirty()` только при изменениях.
- `WarEventLog` — кольцевой буфер с лимитом из конфига.
- Команды: `/waroftherift status`, `/waroftherift log [n]`.
Приёмка: G4 (сериализация туда-обратно), G6 (перезапуск сервера сохраняет данные), нет ссылок на живые объекты в моделях.

## Этап 4. Порталы и старт вторжения

- `PortalRegistry`: события создания портала (`BlockEvent.PortalSpawnEvent`), пересечения (`EntityTravelToDimensionEvent`), ограниченный локальный POI-поиск вокруг игрока (без глобального поиска). Сопряжение пар Overworld↔Nether.
- Условие первого запуска войны: см. A19 в ARCHITECTURE.
- Команды: `/waroftherift portals`.
Приёмка: G5 — построить портал, пройти, убедиться в записи в реестре и журнале; повтор события не дублирует запись; перезапуск сохраняет.

## Этап 5. Поселения

- `SettlementManager` + `SettlementScanner`: ограниченное обнаружение (когда чанки уже загружены игроком/сущностью), дедупликация, оценка населения/обороны/гарнизона по счётчикам, а не сканом мира.
- Статусы поселения: `STABLE`, `THREATENED`, `UNDER_ATTACK`, `FALLEN`, `ABANDONED`.
- Команды: `/waroftherift settlements`.
Приёмка: G5, лимит числа записей из конфига, запись переживает перезапуск, деревни находятся без forced-чанков.

## Этап 6. Модель вторжения

- `InvasionManager`: интенсивность (0–N), стадии (`DORMANT → PROBING → FOOTHOLD → ASSAULT → OCCUPATION`), плацдармы (`FrontRecord`/`BeachheadRecord` в данных), расписание волн по игровому времени, лимиты.
- Адаптация интенсивности: функция от числа открытых порталов, давления, потерь сторон, множителя конфига.
Приёмка: G4 — детерминированность (одинаковый сид → одинаковый ход); G6.

## Этап 7. Стратегическая симуляция

- `WarSimulationManager` + `StrategicBattleResolver` + `WarRandom`: шаг по расписанию (не каждый тик), расчёт сил, потери, захват/потеря территории, падение поселений, беженцы (как данные), логирование.
- Ограниченный «догон» шагов после долгих пауз (`/time add`).
Приёмка: G4 (детерминизм, границы значений, отсутствие NaN/отрицательных сил), G6; в коде нет обращений к `Level`, чанкам, спавну.

## Этап 8. Новые существа

- `SettlementGuardEntity`, `RiftCommanderEntity`: атрибуты (`EntityAttributeCreationEvent`), собственные цели ИИ, сохранение NBT, регистрация (`ModEntities`), яйца призыва, лут, локализация, рендереры на основе ванильных гуманоидных моделей и реально существующих текстур (без битых ссылок).
- Привязка к фракциям через теги.
Приёмка: G2/G3, существа спавнятся командой `/summon`, сохраняются/загружаются, не вызывают ошибок рендера.

## Этап 9. Боевое взаимодействие фракций

- `FactionCombatSystem` + `FactionRelation`: матрица отношений (поселения↔легион враждебны; разорители↔легион враждебны «по ситуации»; поселения↔разорители враждебны; разорители не союзники жителей).
- Две ветки интеграции: `Mob` с `GoalSelector` (добавление целей один раз на `EntityJoinLevelEvent`, защита от дублей меткой NBT) и мобы на `Brain` (пиглины, брюты, хоглины, зоглины, жители) через `MemoryModuleType.ATTACK_TARGET` и `LivingChangeTargetEvent` (см. A4).
- Ограничение частоты поиска целей, радиус из конфига, игнор игрока по настройке.
Приёмка: G5 — наблюдаемые бои между фракциями, отсутствие всплесков TPS, нет «дружественного огня» внутри фракции.

## Этап 10. Материализация боёв (стратегия ↔ реальность)

- `BattleMaterializer`: когда игрок входит в радиус активации и чанки фронта загружены, создаёт ограниченные реальные группы из стратегических сил (бюджет спавна за тик, лимиты, метка `batchId`).
- `BattleReconciler`: при выходе игрока (гистерезис) или завершении боя переносит результаты (потери по событиям смерти, выжившие по счётчикам) в `FrontRecord`; закрытие `batchId`; «поглощение» потерянных реальных сущностей, вернувшихся из выгруженных чанков.
- Обработка зомбификации пиглинов/хоглинов в Верхнем мире (см. A9).
Приёмка: G5 — фронт не флапает, суммарная сила фронта сохраняется (инвариант: материализовано + остаток = было − потери), лимиты соблюдены, перезапуск посреди боя не дублирует мобов.

## Этап 11. Последствия войны

- Падение и захват поселения: смена статуса, беженцы (миграция жителей в безопасные поселения при загруженной области, иначе только данные), метки территории.
- Неразрушающие по умолчанию последствия; опциональные декоративные (отключаемые) эффекты вокруг плацдармов.
- Восстановление: поселение возвращается, когда контроль возвращён.
Приёмка: игрок-постройки не удаляются; изменения сохраняются; журнал отражает события.

## Этап 12. Сеть и интерфейс журнала

- `NetworkHandler` (`SimpleChannel`, версия протокола), пакеты: запрос снимка (C2S), снимок войны (S2C, ограниченный размер, пагинация).
- `WarSnapshot` (DTO), `WarSnapshotFactory` (сервер), `ClientWarState`, `WarJournalScreen` (вкладки: обзор, фронты, поселения, порталы, история, потери).
- Открытие: клавиша (`RegisterKeyMappingsEvent`) и команда; предмет журнала — опционально позже.
Приёмка: G3 — экран открывается в одиночной игре и на выделенном сервере; на сервере клиентские классы не загружаются; запросы ограничены по частоте.

## Этап 13. Команды и диагностика

- Полный набор `/waroftherift` (уровень 2): `status`, `intensity set|get`, `portals`, `settlements`, `fronts`, `log`, `simulate <steps>`, `materialize <front>`, `debug on|off`, `reset confirm`, `config reload` при необходимости.
- Диагностика производительности: счётчики шагов, время шага, число материализованных мобов.
Приёмка: все команды покрыты ручным сценарием, права проверены, `reset` требует подтверждения.

## Этап 14. Баланс, производительность, надёжность

- Профилирование (время шага симуляции, события спавна, цели ИИ), бюджеты в конфиге.
- Многопользовательская проверка (несколько игроков в разных измерениях), выделенный сервер, одиночная игра с повторным входом в мир (очистка `WarRuntime`).
- GameTest-набор для ключевых инвариантов.
- Совместимость: чужие мобы по тегам, датапак-переопределение тегов.
Приёмка: целевые показатели из конфига соблюдены (напр., шаг симуляции — единицы мс), ни одного исключения в 2–3-часовой тестовой сессии.
